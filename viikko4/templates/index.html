$ man how-server-b-was-created

In cPouta I took a snapshot of server A called server-a and launched a new instance server-b from it, with the same flavor (standard.tiny) and security groups. Server B got its own floating IP 128.214.255.14 and the internal IP 192.168.1.118. Server A is 195.148.21.192 / 192.168.1.228, and its week 2 and week 3 pages kept running the whole time.

After cloning, I made B its own server:

  • Changed the hostname to server-b.
  • Disabled the copied week 2 app with systemctl disable --now viikko2, because on B the counter must never be written.
  • Deleted /var/lib/mysql/auto.cnf, so MySQL created a new server_uuid. The clone had the same UUID as A, and replication does not work if the source and the replica share one.

$ man users-and-permissions

Linux users:

  • root on B runs the backup from cron and owns the backup key, the archives and the log. Normal users cannot read them.
  • ubuntu on A is the account the backup logs in to. In A's authorized_keys the backup key has from="192.168.1.118", so the key only works from server B. The website files are world-readable, so no sudo is needed on A.
  • ubuntu on B runs this page as a systemd service. The service reads its password from /etc/viikko4.env, which only root can read.
  • mysql owns the database files on both servers.

On B the copied viikko2 user was removed, and the whole server runs with super_read_only = ON. Even root gets ERROR 1290 when trying to change the counter. Only the replication thread can apply changes from A.

$ cat /etc/cron.d/website-backup 
# Back up server A's /var/www/html to server B once per hour (at minute 30).
30 * * * * root /usr/local/sbin/website-backup.sh

Server B pulls the backup from A, so A does not need any access to B. Every hour at minute 30 the script runs tar on A over SSH and saves the stream as a timestamped archive on B. I chose minute 30 because the week 3 report on A is rewritten at the start of every minute, and :30 is far from the full hour when other jobs usually run.

  • The archive is first saved as .part and checked with tar -tzf. Only a working archive is renamed to .tar.gz, so broken copy never looks like a real backup.
  • Every run writes OK with the file name and size, or FAILED, to the log.
  • The newest 48 archives are kept, which is two days of hourly backups. Older ones are deleted.
  • umask 077 makes every new file readable by root only.
$ man replication

The assignment mentions MariaDB, but my servers already ran MySQL 8.0 from the week 2, so I used MySQL replication instead. The idea is the same, only some commands have new names, for example CHANGE REPLICATION SOURCE TO instead of CHANGE MASTER TO.

  • Server A writes every change to a binary log (log_bin, binlog_format = ROW, server-id = 1). MySQL listens only on localhost and the internal address 192.168.1.228, not on the public IP.
  • Server B (server-id = 2) connects to A as replicator, copies the log into its relay log and applies the changes. replicate-do-db = viikko2 limits replication to the counter database.
  • To start, I made a dump of A with mysqldump --single-transaction --source-data=2. It saves the binary log position (mysql-bin.000001, 1056), so B knows exactly where to continue. The dump was deleted after importing it.
  • GET_SOURCE_PUBLIC_KEY = 1 is needed because MySQL 8 uses the caching_sha2_password login method.
$ man replication-vs-backup

Replication is not a backup. It copies every change to B within a second, including also mistakes. If someone runs DELETE or DROP TABLE on A, the same thing happens on B right away, and there is no older version to go back on. Replication protects against losing a server, but backups protect against losing the data. That is why the website files are backed up as timestamped archives, which keep the history of the last two days.

$ cat lesson-learned.txt

After writing B's replication.cnf with nano and restarting MySQL, SELECT @@server_id, @@read_only still returned 1 and 0. The file looked fine in nano, but cat showed that all settings were on one long line. The line breaks were lost when I pasted the text, and MySQL ignored the broken line without any error. my_print_defaults mysqld confirmed that MySQL did not read my settings. I wrote the file again with printf '%s\n' ... | sudo tee, checked it with cat -A (every line must end with $), and after a restart the result was 2, 1, 1. The lesson: always check that a config change is really in use =D
