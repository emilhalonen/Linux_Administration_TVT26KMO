$ man how-server-b-was-created
  • I created a snapshot of server A in cPouta and launched a new instance, server-b, from it.
  • Server B has its own floating IP 128.214.255.14 (internal 192.168.1.118). Server A is 195.148.21.192 (internal 192.168.1.228).
  • I changed the hostname to server-b.
  • I disabled the copied week 2 app on B, since B must never modify the counter.
  • I deleted /var/lib/mysql/auto.cnf so that MySQL generated a new server_uuid for B. The clone had the same ID as A, which prevents replication from working.
  • Server A and its week 2 and week 3 pages remained online throughout.

$ man users-and-permissions

Linux users:

  • root on B runs the backup job and owns the archives, the SSH key and the log.
  • ubuntu on A is the account the backup connects to. In A's authorized_keys the backup key is restricted with from="192.168.1.118", so it only works from server B.
  • ubuntu on B runs this page as a systemd service.
  • mysql owns the database files on both servers.

MySQL on B runs with super_read_only = ON, so not even root can modify the data. Only the replication process is allowed to apply changes from A.

$ cat /etc/cron.d/website-backup 
# Back up server A's /var/www/html to server B once per hour (at minute 30).
30 * * * * root /usr/local/sbin/website-backup.sh
  • Cron runs the backup script every hour at minute 30.
  • Server B pulls /var/www/html from A over SSH and saves it as a timestamped .tar.gz archive.
  • Each archive is verified before it is saved, so a broken copy is never kept.
  • Every run logs either OK or FAILED.
  • The 48 most recent backups (two days) are kept, and older ones are removed automatically.
$ man replication

The weekly task refers to MariaDB, but my servers were already running MySQL 8.0 from week 2, so I used MySQL replication instead. Anyways the principle is the same :)

  • Server A records every database change in a binary log.
  • Server B connects to A as replicator, reads the log and applies the same changes to its own copy.
  • Only the viikko2 database is replicated.
  • MySQL on A is reachable only from the internal network, not from the internet.
  • To get started, I copied the database from A to B with mysqldump. Since then, replication has kept B up to date. The dump file was deleted afterwards.
$ man replication-vs-backup

Replication does not replace backups. It copies every change to B immediately, including mistakes: if a table is deleted on A, it disappears from B as well. Backups store earlier versions, so the data can be restored after an error.

$ cat lesson-learned.txt

After editing B's MySQL configuration with nano and restarting MySQL, the new settings had no effect. Running cat on the file showed that all settings were on a single line: the line breaks had been lost when I pasted the text, and MySQL silently ignored the line. I rewrote the file with printf, verified it with cat -A, and after a restart the settings were active. The lesson: always confirm that a configuration change is actually in use =D

The same lesson came up again with cron: the first scheduled backup at 16:30 never ran. The cron file had no newline after its last line, and cron ignores a final line without one. After adding the newline, I checked the end of the installed file with tail -c 1 ... | od -c.
